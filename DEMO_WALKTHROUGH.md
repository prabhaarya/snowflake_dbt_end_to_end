## 🎬 Step-by-Step Live Demo Script

### Act 1: The Setup & Modularity (1 - 2 mins)

**What to Say:**
> *"Today we're looking at a modern analytics engineering pipeline built on Snowflake using dbt. Everything is defined in code: dependencies, warehouse sizing, materializations, and data tests."*

**What to Show in Code:**
- Open [`dbt_project.yml`](dbt_project.yml) to highlight:
  - Staging layer configured to materialize as **Views** on warehouse `DWH_MIGRATIONS`.
  - Intermediate layer configured as **Ephemeral** (compiled directly into downstream queries, saving storage).
  - Marts layer configured as **Tables**.

**Command to Run:**
```bash
dbt deps
```
*Key talking point:* Package manager downloads community and vendor verified macros (`dbt_utils`, `snowflake_utils`).

---

### Act 2: Executing Transformations (`dbt run`) (2 - 4 mins)

**What to Say:**
> *"Now let's build the entire dimensional model in Snowflake. dbt determines the dependency graph (DAG) automatically and executes independent models in parallel threads."*

**Command to Run:**
```bash
dbt run
```

**Expected Flow on Screen:**
1. `stg_customers` & `stg_orders` execute concurrently as Views.
2. `int_customer_orders_summary` is compiled in memory as an ephemeral CTE.
3. `dim_customers` (Table) and `fct_daily_sales` (Incremental Table) build concurrently.

**Live Validation in Snowflake UI:**
- Switch to Snowflake Worksheet:
  ```sql
  -- Show created tables and views
  SHOW OBJECTS IN SCHEMA TOMWALL_DB.TOMWALL_SCHEMA2;
  ```
- *Key talking point:* Notice `int_customer_orders_summary` is NOT in Snowflake! It was inlined into `dim_customers` via zero-storage CTE interpolation.

```bash

```
*Key talking point:* All tests pass with zero SQL boilerplate written by hand.

### Act 4: Snowflake Cost & Compute Optimization (6 - 8 mins)

**What to Say:**
> *"Cloud data warehousing costs matter. We've built two Snowflake-native optimizations into our marts:"*
> 1. *"Clustering Keys: `dim_customers` clusters by `customer_id` and `fct_daily_sales` by `sales_date` for micro-partition pruning."*
> 2. *"Incremental Loading: In production, fact tables shouldn't be rebuilt from scratch every day."*

**What to Show in Code:**
- Open [`models/marts/fct_daily_sales.sql`](models/marts/fct_daily_sales.sql):
  - Highlight `{% if is_incremental() %}` and the 3-day lookback window (`dateadd('day', -3, ...)`).

**Commands to Run:**
```bash

# Show full-refresh capability when historical recalculation is required
dbt run --select fct_daily_sales --full-refresh
```

## 💡 Quick Q&A Cheat Sheet for Presenters

**Q: How is dbt different from an ETL tool like Informatica or Fivetran?**
> *A: Fivetran/Airbyte handles the 'E' and 'L' (Extraction & Loading raw data into Snowflake). dbt handles the 'T' (Transformations), running 100% inside Snowflake utilizing its native SQL engine and compute power.*

**Q: How does dbt handle environment separation (Dev vs Prod)?**
> *A: Through targets in `profiles.yml`. Developers build into personal sandbox schemas (e.g. `DEV_SCHEMA`), while CI/CD runs with `--target prod` into production analytics databases without changing a single line of model SQL.*

**Q: What happens if a test fails in production?**
> *A: In CI/CD, `dbt build` halts downstream execution immediately (`--fail-fast`). Bad data is caught before it enters production marts or BI dashboards.*
